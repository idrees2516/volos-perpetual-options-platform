Engineering blueprint for a high-performance, security-first onchain Volatility OS
I went deeper into the implementation details behind Derive, Paradex, Paradigm, Aevo, Panoptic V2, Rysk, Block Scholes, Pyth, Safe/ERC-4337, ERC-7579, EIP-712 and intent/solver architectures.

The main architectural conclusion is stronger after this pass:

Do not build the product as one giant protocol.

Build it as a hybrid system in which low-latency price discovery, strategy construction, risk simulation, RFQ and routing happen offchain, while custody, authorization, hard spending constraints, signatures, settlement invariants and the most important safety rules remain cryptographically or onchain enforced.

This is already the direction taken by serious derivatives venues. Derive combines an offchain CLOB with self-custodial onchain settlement on an OP Stack chain. Aevo similarly uses offchain matching with onchain positions and settlement and currently advertises sub-10ms exchange latency. Paradex is targeting below 50 ms P95 order-creation latency and exposes 50 ms binary/SBE market-data feeds. (docs.derive.xyz)

The optimal product therefore looks less like “another DEX” and more like this:

user intent → strategy compiler → volatility/risk engine → execution optimizer → RFQ/CLOB/solver network → venue settlement → smart-account policy enforcement → persistent automation → reconciliation.

The fundamental architecture
I would divide the system into four security/performance domains.

| Domainat belongs there | Latency requirement | Trust model | |---|---|---:|---| | Hot trading plane | Market data, pricing, Greeks, routing, RFQ, maker quoting | µs–ms internally | Can be offchain because results are independently verifiable | | Risk/control plane | Portfolio risk, policies, collateral allocation, automation | ms–seconds | Deterministic and auditable | | Custody/authorization plane | User assets, policy limits, nonces, signatures, spending permissions | Blockchain latency acceptable | Trust-minimized/onchain | | Analytics/data plane | Historical data, P&L, TCA, backtesting, research | seconds–minutes | Eventually consistent |

Trying to put the hot trading plane onchain will make the system slower and more expensive without meaningfully improving custody security.

Trying to put the custody plane entirely offchain destroys much of the reason for building this product onchain.

The key is choosing the boundary correctly.

What should be onchain and what should stay offchain
My recommended boundary is:

Order-book reconstruction
Every venue connector should maintain its own deterministic book.

The process should be:

snapshot → apply deltas → verify sequence → detect gap → freeze venue → reacquire snapshot → resume.

If a sequence gap appears:

never continue quoting from a potentially corrupt book.

Mark:

Backpressure
A slow consumer should never block market-data ingestion.

Hot-path callbacks should do almost nothing.

The RFQ engine
This needs to become one of the platform's strongest pieces of infrastructure.

RFQ state machine
A serious RFQ needs explicit states:

CREATED → DISTRIBUTED → QUOTING → QUOTE_SELECTED → EXECUTING → PENDING_SETTLEMENT → FILLED / REJECTED / EXPIRED.

This matters because asynchronous APIs do not mean “trade done.”

Paradex's RFQ create and execution endpoints return 202 Accepted merely to indicate that a request has been queued; actual success or failure arrives later through WebSocket events. Paradigm similarly distinguishes pending settlement, filled and rejected trades. (Paradex Documentation)

Your internal state machine must mirror that reality.

Idempotency
Every state-changing operation must have an idempotency key.

Network timeout cannot mean:

“Let's submit it again and hope.”

It must mean:

“Query the state of request X.”

Otherwise automated strategies will eventually create duplicate trades.

Solver standard

An options-specific Strategy Quote Protocol could borrow this architecture.

Automation workflow
Every policy cycle should do:

obtain consistent snapshot → calculate desired state → calculate portfolio diff → simulate risk → request executable quotes → verify policy → execute → wait for settlement → reconcile → persist new state.

Do not schedule:

“buy an option every Friday.”

Schedule:

“at Friday's evaluation, determine whether the existing position needs a roll.”

That distinction makes retries safe.

Use durable workflows
This is a good use case for a durable workflow engine such as Temporal or an equivalent event-sourced orchestrator.

A roll may span:

quote requests;

timeouts;

maker responses;

chain confirmations;

venue acknowledgements;

retries;

manual intervention.

A normal cron job is not sufficiently robust.

Prevent duplicate automation
Every policy evaluation needs:

policy_id

evaluation_epoch

plan_hash

execution_id.

If the worker crashes after submitting the trade but before saving its database state, the resumed workflow must recognize the existing execution_id rather than creating another trade.

Auto-roll logic
A roll should not simply fire at exactly 7 days to expiry.

That makes user flow predictable to market makers.

Instead define a roll window, e.g.:

7–10 DTE.

Then execute when:

spread;

IV;

carry

meet the policy criteria.

This reduces market impact.

Atomic rolling
Treat:

sell old put + buy new put

as one strategy.

Do not sell protection and then separately attempt to buy the replacement.

The trade should become a calendar spread RFQ.

This is exactly where strategy-native execution becomes powerful.

Liquidation architecture
Liquidating options as independent positions can be extremely dangerous.

The liquidation engine should auction:

Partial liquidation
Only enough risk should be removed to restore an account to a safety target.

That is the model I would use.

Liquidation target

130–150%.

The most important security separation
I would define three independent trust boundaries:

Strategy system
Can suggest what trade to perform.

Cannot move funds.

Risk/policy system
Can approve that a proposed trade fits rules.

Cannot change rules.

Execution account
Can execute only if cryptographic/onchain authorization conditions are satisfied.

Compromising one component should not compromise the entire system.

The most important operational rule
Never let:

price discovery

and

liquidation reference price

depend exclusively on the same venue.

Otherwise an attacker can manipulate the venue and trigger favorable liquidations using the manipulated value.

Execution pricing and risk reference pricing must maintain independence.

The most important performance rule
Never perform expensive full-portfolio calculations repeatedly if the change is incremental.

Cache:

scenario prices;

current portfolio scenario vector;

Greeks;

surface parameters;

forward curves.

Then incoming trades become vector updates.

This is how the risk engine becomes fast enough for professional execution.

The most important routing rule
Never optimize an option leg independently when the user wants a strategy.

Optimize:

economic package price.

Paradigm's multi-leg atomic RFQ architecture and Paradex's current 25-leg RFQ implementation are strong real-world validations of that design direction. (Paradigm Documentation)

The most important automation rule
Never give an agent unrestricted wallet authority.

Use constrained capabilities.

Safe explicitly warns that modules have significant execution power and must be treated as security-critical, while ERC-4337/7579 give us the architectural tools to build modular permissions. (Safe Docs)

The most important long-tail rule
Permissionless listing must not imply permissionless leverage.

Anyone might create a market.

That does not mean the protocol should permit:

10× naked short options

against an illiquid token.

Risk permissioning and market permissioning can be separated.

The most important perpetual-options insight
I would not initially expose perpetual options as a separate market category.

Expose:

Persistent exposure.

Then let the optimizer choose:

true perpetual option;

auto-rolled dated option;

call spread;

Panoptic-style exposure;

other future primitive.

That makes the frontend resilient to whichever implementation eventually wins.

What I now think the product should be
After this deeper engineering research, I would define the company as:

A self-custodial volatility execution and risk network.

Not:

decentralized options exchange.

The first layer is intent.

The second is risk.

The third is liquidity aggregation.

The fourth is persistent automation.

The fifth is distribution.

Only later should it own the actual option primitive and clearing venue.

The architecture gives you the best combination of:

performance — because pricing/routing/risk optimization stay offchain and heavily cached;

security — because custody and hard permissions stay onchain and agents have bounded capabilities;

capital efficiency — because strategy-level risk is recognized and collateral is intelligently allocated;

liquidity efficiency — because RFQ, CLOB and solver liquidity are treated as one network;

UX efficiency — because users interact with financial outcomes rather than strike/expiry mechanics;

future optionality — because a persistent position can migrate between dated options, perpetual options, RFQ contracts and future primitives without forcing the user to change their mental model.

The biggest technical work is therefore not building another smart contract. It is getting the combination of risk engine + strategy compiler + RFQ/router + persistent policy engine + constrained smart account correct. Those five components are where I would concentrate the strongest engineering team and most of the security budget.
